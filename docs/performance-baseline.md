# 识别性能优化实验报告

> 目标：在不降低防伪强度的前提下压缩单次认证耗时。每改一项立刻实测耗时与精度。
>
> **硬约束（全程不动）：** 匹配阈值 0.80（默认，可配置，钳到 0.70–1.00）、`anti_spoof_threshold=0.281`、best/2nd ratio=0.75、PAD 5/5 全过、**3 次身份绑定**（融合循环帧 1/3/5；原独立的 `CONSENSUS_FRAMES=3` 循环已在实验 7 并入融合循环删除）。

## 测试环境

| 项目 | 值 |
|---|---|
| CPU | AMD Ryzen 9 7945HX（16 核 / 32 线程） |
| 摄像头 | 内置，1280×720 @ NV12（实验 2 起降为 640×480） |
| 运行模式 | MF（standalone 前台）为主；第 5 节补 DS（Session 0 生产）复测 |
| 采样 | 解析 `service.log` 毫秒时间戳，每项改动后连续 6–9 次锁屏解锁取均值 |

## 基线（干净 HEAD，7 次连续成功认证）

端到端 **avg 2659ms**，各环节占比：

```
相机初始化   254ms  (10%)  ██████▏
曝光+首帧    672ms  (25%)  ██████████████▏   ← 含 5×50ms=250ms 固定 sleep
一致性3帧    309ms  (12%)  ██████▏
PAD 5帧     977ms  (37%)  ██████████████████████▏   ← 最大块
后置验证     139ms  ( 5%)  ███▏
```

精度快照（21–35 帧）：匹配距离 avg 0.572（阈值 < 0.80，余量 0.23），PAD fused avg 0.965（阈值 ≥ 0.281，余量 0.68），7/7 成功。**余量充足，后续无损优化不会触及精度边界。**

优化优先级（按可压缩量）：PAD 阶段（977ms）> 曝光丢弃 sleep（250ms）> PAD pacing sleep（500ms）> 采集分辨率。

## 1. 实验 1：双 MiniFAS 并行（commit 2596a10）

**改动：** `OnnxAntiSpoof::Predict` 用 `std::async` 并行跑 V2/V1SE（各自独立 session/env，无共享状态）。

**结果：** PAD 单帧推理 144→134ms（−7%），端到端 2659→2615ms（−44ms）。

**精度：** 融合公式逐帧自检 30/30 通过，证明无数据竞争。低分会话是真实光照变化，非回归。

**判定：保留。** 收益小（模型太轻，线程开销抵消大半），但无损且代码更合理。

## 2. 实验 2：采集分辨率 1280×720 → 640×480（commit 2596a10）

**改动：** `FaceService.cpp` 三处 `Initialize` 改 640×480（叠加在实验 1 之上）。摄像头原生支持 640×480 NV12，协商成功。

**结果：** PAD 单帧推理 134→125ms（每帧 YUV 转换量减 67%），端到端 2615→2519ms（相对基线 −140ms）。

**精度：** 匹配距离 0.572→**0.553**（更近，零退化——640×480 与 SCRFD 640 输入对齐，减少了 720→640 的拉伸畸变），PAD 全 1.000，7/7 成功。

**判定：保留。** 明确赢家，与 SCRFD 输入对齐是更合理的采集分辨率。

## 3. 实验 3：缩短保守 sleep（commit 2596a10）

**改动（叠加在实验 1+2 之上）：**
- 曝光丢弃：5 帧 × 50ms（250ms）→ 3 帧 × 20ms（60ms）
- PAD 帧间 pacing：100ms → 60ms（保留非零间隔维持时序多样性防重放）

**结果（稳态 S2-S7）：** 端到端 2519→**2156ms**，相对基线 −503ms（−18.9%）。曝光段 −188ms（sleep 主导），PAD 段 −226ms（pacing 主导）。

**精度：** 匹配距离 0.562（与基线 0.572 持平），PAD 全 1.000，7/7 成功。3 帧 × 20ms 已让曝光稳定，5 帧 × 50ms 是过度保守。

**判定：保留。** 三项里收益最大，纯 sleep 削减零计算成本。

## 4. 实验 4（perf2）：ONNX 线程 cap 4 → 8（commit c0003cb）

**改动：** `OnnxThreadCount()` cap 从 4 提到 8。`FACELOGIN_ONNX_THREADS` 环境变量覆盖保留。

**动机：** w600k_r50 卷积层 intra-op 并行度高，16c/32t 机器余量充足。低核机器通过 `cores/2` 自然降级（4 核机 = 2 线程），不会卡顿。

**结果（9 次稳态）：** PAD 单帧推理 127→**95ms**（−34%），端到端 2156→**1876ms**，累计相对基线 **−801ms（−30.1%）**。

**精度：** 匹配距离 0.556，PAD 0.999，9/9 成功，16 核机器无卡顿。

**判定：保留。** 性价比最高（一行 cap 值省 298ms）。

## 5. 生产环境复测（DS / SCM 服务模式）

用 wails build 产出安装器（内嵌 perf2 service.exe），安装后 SCM 服务在 Session 0 跑 DirectShow。锁屏解锁 7 次。

| 验证项 | 结果 |
|---|---|
| DS 640×480 协商 | ✅ `IAMStreamConfig::SetFormat` 成功，未走 fallback |
| 精度 | ✅ 匹配距离 avg 0.542，PAD fused 全 1.000，7/7 成功 |
| 端到端 | **2156ms**（比原始 MF 基线 −503ms / −19%） |

## 6. 实验 5（perf3）：重型模型后台懒加载（commit 3c06e88）

**动机：** 前 4 项压缩稳态耗时，但冷启动（开机后服务刚启动）w600k_r50(174MB) + 双 MiniFAS 同步加载会延迟 pipe 监听数秒。

**改动：** SCRFD(15.5MB) 同步加载保 pipe 尽快上线；w600k_r50 + 双 MiniFAS 移入后台线程。`EnsureModelsLoaded` 认证开头等待就绪（fast path 仅 atomic load），`AbortModelLoadWait` 在 Stop 里安全 join。

**冷启动（关键收益）：** pipe 监听比模型就绪早 **260ms**（MF）/ **266ms**（DS）。热启动实测，冷启动（开机首次磁盘冷）收益到秒级。无死锁/崩溃。

**稳态（精度+耗时）：** 匹配距离 0.585，PAD 全 1.000，7/7 成功。初测 +89ms 经临时埋点定位是系统波动（同代码重测波动可达 ±700ms），`EnsureModelsLoaded` fast-path 实测 0–13μs，**无真实稳态回归**。

**判定：保留。** 补上了前 4 项缺失的冷启动维度。

## 7. 低性能/散热受限机器实测（2026-08）——多帧全嵌入策略不可行

> 三台机器实测结论：**「每次认证 6 次 r50 嵌入」的多帧共识 + 每帧身份绑定 + PAD 5/5 策略，在低性能或散热受限的机器上不可行**（端到端 5.5–21s），优化空间已穷尽，需要管线级重新设计，不是调参能解决的。

### 实测数据

| 机器 | CPU | 单次嵌入 | 端到端 |
|---|---|---|---|
| 开发机 | Ryzen 9 7945HX（16 全大核，AVX512） | **27ms**（8 线程） | 1.77s |
| 朋友机 | i5-13500H（4P+8E 混合） | 1.4–1.9s（散热受限） | 16.6–21s |
| 第三台 | i7-1360P（4P+8E 混合） | 0.35s（散热正常 4.4GHz）/ 1.6–1.9s（降频 2GHz） | 5.45s / 14–15s |

### 根因链（按影响排序）

1. **每次认证 6 次嵌入**（一致性 3 + PAD 锚定 2 + 最终验证 1）是架构成本，任何机器都付；7945HX 上每次仅 27ms 所以无感，低性能机器上放大成 2–12s。
2. **CPU 频率是唯一决定性变量**：同一台 i7-1360P，4.4GHz 时嵌入 0.35s、端到端 5.45s；过热降频到 2GHz 时嵌入 1.6s、端到端 15s——**频率差 2.2 倍，端到端差 3 倍**。笔记本持续 AVX 负载（r50 嵌入）撞温度墙降频是常态，插电/电源模式无法根治，需散热维护。
3. **混合架构（P+E 核）异构同步惩罚**：`OnnxThreadCount()` = 核数/2（4P+8E → 8 线程）跨 P/E 核并行，每层归约等最慢的 E-core，并行收益被同步吞掉。实测 `FACELOGIN_ONNX_THREADS=4` 在 4P+8E 机器上是合理配置（4 线程可全落 P-core），但收益被频率波动淹没，未做代码级自动检测。
4. **DS 低光抓帧**：暗光下相机自动曝光拉长，帧率掉到 ~3fps，每帧多等 0.1–0.7s——次要因素，但进一步恶化慢机器体验。

### 已验证无效/不可行的方向

- **换 w600k_mbf 轻量模型**：同协议同维度但同人距离 p50 0.792 贴死 0.80 阈值（详见 `threshold-calibration.md` 附录），侧脸余量归零——**否决**。官方轻量档只有 MobileFaceNet 一个选择，不存在"更小且接近 r50"的中间档。
- **PAD 5/5 降帧数 / 砍身份绑定 / 降阈值**：直接弱化 bug3 照片攻击防线，**不在性能优化范围内**。

### 未竟方向（需安全评估或管线重设计）

- 一致性 3→2 帧：省 1 次嵌入（~0.8s/次），3 帧防的是光照闪变单帧误报，2 帧仍可挡——**唯一不伤防伪强度的大优化**。
- ONNX 线程 P-core 亲和性（`GetLogicalProcessorInformationEx` 枚举）：混合架构嵌入 0.35s → 理论 ~0.15s。
- 若性能是硬需求：认证管线需重设计（如两级匹配：轻量模型粗筛 + r50 精确认），这是新架构决策，超出本报告范围。

### 结论

**在保持当前安全强度（PAD 5/5、3 帧共识、每帧身份绑定）的前提下，低性能机器的合理下限是 4–5s（散热正常 + 一致性 2 帧 + 线程亲和性）。** 若目标 < 2s，必须重新设计认证管线，且任何设计都必须先过 bug3 照片攻击防线评估。

## 8. 实验 6（2026-08）：r50 INT8 量化——1.68× 嵌入加速（已采用）

> 第 7 节结论之后唯一落地的"纯工程、零安全语义"大优化。所有安全阈值、PAD、匹配逻辑未动，只是嵌入模型换成量化产物。

### 动机

低性能机器的端到端耗时大头就是 6 次 r50 嵌入（降频机 9.6s / 15s = 64%）。换轻量模型已否决（mbf 同角度 p50 0.792 贴死 0.80，见 threshold-calibration.md 附录）；"流水线化"（在途嵌入期间抓下一帧）经核算只重叠帧间隔 ~0.1s，不值得做。**压嵌入本身的唯一零语义手段是 INT8 量化**。

### 方法

- **量化路径**：onnxruntime `quantize_static` QDQ 格式，**per-tensor**（r50 是 opset 11，per-channel 需 opset 13）。dynamic 路径生成 `ConvInteger` 节点，CPU EP 不实现、加载即失败——已废弃（`quantize_r50.py --dynamic` 保留作参考）。
- **Calibration**：lfw_subset 每身份 2 张真实照片的 112×112 chips（78 张，calibrate.py 同款管线），跑真实 activation 分布。
- **Python 1.19.2 标定**（同一批 26 张自拍，18 张嵌入成功，与 mbf 附录同口径）：

| 分布 | FP32 | INT8 | 偏移 |
|---|---|---|---|
| 同角度对 p50 | 0.665 | 0.706 | +0.041 |
| 跨角度对 p50 | 0.879 | 0.921 | +0.042 |
| me vs 58 陌生人 min | 1.266 | 1.289 | 持平 |

- **C++ 1.23.2 生产验证**（新增 `tools/embedding_test/EmbeddingTest`，同一批 18 张 chip 喂生产 `OnnxRecognizer`）：同角度 p50 FP32 **0.6647** ↔ Python 0.665（管线数值对齐再获证实）→ INT8 **0.6938**（余量 0.106，mbf 只有 0.008）；嵌入 15.16 → **9.03 ms（1.68×）**；18/18 成功，512-D。

### 集成

- `FaceService.cpp` `kRecognizerSha256` → INT8 模型哈希（完整性校验保持 fail-closed）
- Go 安装器 manifest（size + SHA）同步；`download_models.ps1` 改为"下载 FP32 源 → 本地量化 → pinned 校验"链路
- 模型 174 MB → 44 MB，**安装包 252 → 122 MB**

### 开发机 DS 实测（安装版，8 次全部成功）

| 指标 | FP32（第 5 节复测） | INT8 | Δ |
|---|---|---|---|
| 端到端（稳态 7 次均值） | 2.156s | **1.455s** | **−32.5%** |
| 匹配距离 | avg ~0.56 | avg ~0.56 | 无退化 |
| PAD fused | 全 1.000 | 全 0.97+ | 无退化 |

单次 1.394–1.535s；唯一 8.3s 异常为用户 7s 未看镜头（看到脸后 3 帧 266ms 即过）。

### 外推与结论

- 低端机预期：4.4GHz 混合架构 5.45s → **~4.6s**；降频 2GHz 15s → **~11s**（温度墙仍占大头）。
- 量化误差是**系统性 +0.03~0.04 均匀偏移**（同角度/跨角度一致上移、异人持平），与 mbf 的"特征空间本就差"不同——这是它可用的根本原因。
- 余量 0.106 仍显著；若未来需要更多余量，可升级 opset 13 + per-channel（预计误差减半），或重录模板归零偏移。
- 已录入模板**无需重录**（+0.03 偏移在实测噪声内）；边缘用户重录一次即可归零。

## 9. 实验 7（2026-08）：共识 + PAD 合并循环——4 嵌入/认证（已实现，待实测）

> 第 8 节之后唯一不放松任何已定安全参数的结构性优化：**把独立的"3 帧匹配共识"阶段与"5 帧 PAD"阶段融合成单一窗口**，每帧同时跑 PAD 与（计划内的）嵌入。所有阈值、PAD 5/5、最终验证原样保留，嵌入总数 **6 → 4**。

### 动机

第 7 节"未竟方向"里共识 3→2 帧需安全评审（防单帧光照闪变误报）；相机保活（DS 建图 514ms）是纯工程项但受 LED 隐私/设备占用约束。合并循环避免了"降帧"这个敏感动作，而是把**身份绑定与活体在帧级重叠**：共识帧不再是"不设防的预检"，而是 PAD 窗口内的 3 次隔帧嵌入。

### 设计（安全参数逐项不变）

| 项 | 合并前 | 合并后 | 判定 |
|---|---|---|---|
| PAD 帧数/阈值/pacing | 5/5，0.281，60ms | **不变** | 每帧都有 PAD（覆盖范围反而扩大：原共识 3 帧完全无 PAD 保护） |
| 首帧身份锚定 | PAD 第 1 个有效帧嵌入 | 不变（第 1 个有效帧嵌入并**锁定身份**，凭据来源） | 决定性绑定 1 次 |
| 尾帧身份锚定 | PAD 第 5 个有效帧嵌入 | 不变 | 决定性绑定 1 次 |
| 中间连续性 | IoU ≥ 0.35 | 不变（第 2/4 帧） | — |
| 隔帧共识 | 连续 3 帧嵌入 | **第 3 个有效帧嵌入**，3 次隔帧嵌入必须同一 SID | 采样独立性更强；决定性绑定总数仍 3 次（首锚+尾锚+最终验证），**一个没少** |
| 最终验证 | 新鲜帧嵌入 = 锁定 SID | **不变** | 防"PAD 过后换脸"窗口不变 |
| 嵌入失败 | 锚定帧顺延 | 不变（顺延帧不计入 PAD 计数、不满足绑定计划） | 共识不可能静默缩水到 2 次 |
| 嵌入匹配到**不同** SID | 拒绝（换脸） | **不变**（fail-closed） | — |
| 全局 15s 超时 | 独立共识循环内检查 | **移入合并循环**（覆盖 PAD 阶段，更严格） | — |

**安全论证要点（评审材料）**：放行门 = PAD 5/5 + 首锚锁定 + 尾锚绑定 + 最终验证，全部原样；嵌入总次数 6→4 的弱化只影响"匹配层冗余"，而匹配层防的"换人"由决定性绑定以同样次数覆盖，防伪层（PAD）参数一个未动。隔帧采样（跨 ~400ms）被一次光照闪变全中的概率低于连续 3 帧（跨 ~200ms）。

### 实测（2026-08-08，开发机，DS 生产模式，安装版，9/9 成功）

| 指标 | 合并前（INT8，第 8 节） | 合并后实测 | Δ |
|---|---|---|---|
| 认证核心（Starting→Credentials） | 1.455s | **1.121s**（1.104–1.161） | **−334ms（−23%）** |
| 匹配距离 | avg ~0.56 | avg **0.599**（0.515–0.662） | 同波动带，无退化 |
| PAD 分数 | 全 0.97+ | 0.784–1.000，45/45 帧全过 | 无退化 |

日志逐帧核验绑定计划精确按第 1/3/5 个有效 PAD 帧执行（`Identity locked [1/3]` → `confirmed [2/3]` → `confirmed [3/3]`），每次认证恰好 4 次嵌入（3 绑定 + 1 验证）；9 次认证无一次超时/换脸拒绝/顺延。

## 11. 实验 10（2026-08-15）：CP 输入触发重构——残留隔离 + 静默 200ms（已采用）

> 修 bug 与提速同体：按住 Win+L 锁屏会"自动解锁"，同时触发路径有 ~450ms 固定等待。

### 动机

1. **锁屏快捷键自解锁 bug**（2026-08-15 17:15 复现）：按住 Win+L 不松手 → 凭据视图提前出现（按住键的自动重复输入把壁纸顶掉）→ 残留输入波（自动重复 + KEYUP）被判定为 dismiss 波 → 静默后自动触发认证 → 人脸在镜头前时**锁屏 ~2s 后自动解锁**（auto-trigger elapsed=47ms）。
2. **触发延迟**：旧实现输入→StartAuth 固定 ~470–500ms（QUIESCE 400 + 轮询 100 粒度）。

### 实现（`credential_provider/FaceLoginCredential.*`）

- `Advise()` 在记录 baseline 的同一时刻同步 `GetAsyncKeyState` 快照仍被物理按住的**任意键**；线程开头的**残留隔离段**：轮询等待全部松开（5s 上限防按键状态卡死）→ 等 150ms 吞最终 KEYUP → 重播种 `lastInputTick` 抬过整串残留。
- `QUIESCE_MS` 400→200、轮询 100→50ms。静默阈值语义是"交互结束检测"而非按键消抖，必须显著大于自动重复间隔（~33ms）与打字间隔（100–300ms）。

### 关键发现（grep 不到的坑）

- **Windows 在激活安全桌面时清除 Win 修饰键的异步状态**：按住 Win+L 时快照见 'L' 而不见 LWIN。修饰键指纹因此不可靠，判定改为任意被按住的键；持续按住的普通键因自动重复刷新而稳定可见。首版修饰键方案实测漏判（20:22 快照 `L — not needed` 仍误触发），改任意键后根治。
- `GetAsyncKeyState` 在 LogonUI 安全桌面内工作正常（实测）。
- 按住键期间壁纸被顶掉是 Windows 行为（任何输入 dismiss 壁纸），凭据页停留是本修复的安全终点，约 30s 后系统自动回退壁纸页；非回归。

### 实测（开发机，安装版）

| 指标 | 旧版 | 新版 |
|---|---:|---:|
| 输入→StartAuth | 470–500ms | **260–293ms**（均值 ~277，5 样本） |
| 按住 Win+L 快松 / 慢松 3.6s | 自动解锁（bug） | 隔离 ARMED→ended（1468/3750ms），触发仅来自后续真实输入 |
| 正常解锁 / 密码输入 | — | 零回归（实测确认） |

### 实验 10 续：静默 200→100ms + 按住守卫——触发 ~277→~125ms（2026-08-15 二轮，已实测）

200ms 静默的"防打字中途触发"地板经产品形态论证后移除：等待视图人脸优先、无密码框持有焦点，输密码需先主动切换磁贴，且交互策略已保证认证启动不打断输入。取而代之的是**触发前按住守卫**——`GetAsyncKeyState` 确认当前无任何键被物理按住才触发（被按住的键仍在产生自动重复 tick，永远不算波结束，其 KEYUP 重启静默窗口），静默阈值因此只需盖过事件抖动（100ms，自动重复间隔实测 33–76ms）。另加 25ms 轮询 + 静默窗口到点精确唤醒。

实测（开发机，安装版，5 样本）：输入→触发 **104–141ms，均值 ~125ms**（= 100 静默 + ~25 固定开销，精确唤醒无轮询浪费）；按住 Win+L 回归仍通过（隔离 1969/1547ms 后触发仅来自真实输入）。触发段累计：原版 470–500 → 277 → **~125ms**。

### 实验 10 三续：残留隔离结构性失效——快照+隔离整体删除，改三规则残留吞没（2026-08-31，后被四续替代）

**用户复现（2026-08-31 22:30–22:35，29/29 轮全部自动触发）**：①按 Win+L 快松 Win、长按 L 数秒再松 → 松 L 即开始识别；②按住 Win+L 一会儿、先松 L 再松 Win → 松 Win 即开始识别。人脸在镜头前时等于"锁屏即自解锁"。当日日志铁证：7.65s 按住轮（22:33:21.686 Advise → 29.333 StartAuth）**无 5s 隔离上限 WARN**——隔离段根本没在等任何键；多轮 Advise→StartAuth 仅 139–213ms（快于人类 dismiss 反应，只能是残留尾巴触发）。

**根因——快照在真实锁屏时序下结构性失明**：Advise/SetSelected 发生在锁屏壁纸仍显示时（壁纸轻点一下触发正依赖线程此时已在跑），而 `GetAsyncKeyState` 在该阶段全盲（通道矩阵 2026-08-29 实测）→ 快照恒空 → 隔离从未武装。8-15 的"快照见 'L'"观察来自时序巧合（该轮 Advise 落在凭据视图已起后），机制本质靠运气。即使快照抓到键，Win 键异步状态被系统清除、隔离轮询也可能在盲区误判已松开提前退出；5s 上限路径则把水位线抬到按键仍按住处、重复尾巴变成新波。四条路全部漏。

**新机制（无快照、无轮询、无上限，三规则全在波逻辑内）**：
1. **波起始间隔规则**：tick 距上一 tick（或 baseline）≥QUIESCE_MS(100ms) 才能开波。按住键自动重复间隔 33–76ms，整条尾巴（含最终 KEYUP，≤76ms 跟在最后一个 repeat 后）永远开不了波，只推进水位线。
2. **残留沉降窗**：锁屏轮 baseline 后 `kResidueSettleMs=600ms` 内 tick 只推进水位线。堵自动重复**初始延迟**（默认 500ms）的空洞——keydown tick 在 baseline 前、首个 repeat tick 落在 baseline 后 100–500ms，间隔规则单独会被这个 ≥100ms 假间隔骗过（本机 B−t0≈250–350ms，首 repeat 落 B+~200ms）。失败重试磁贴沉降窗=0（"按任意键重试"不能吞按压）。
3. **孤立修饰键 BREAK 不算按压**：raw sink 的 BREAK 对普通键仍算按压证据（壁纸轻点机制：KEYDOWN 被吞、KEYUP 漏出），但修饰键 BREAK 需先见过修饰键 MAKE（粘性闩）。Win+L 是唯一手势中途触发的锁屏快捷键，Win 无自动重复（松开前零 tick）+异步状态被清除（GetAsyncKeyState 不可见），其释放=L 链结束后隔 ≥100ms 的孤立 BREAK，与壁纸轻点同形，只能按 VK 身份排除（0xA0–0xA5 及泛型 0x10–0x12）。

**语义代价（有意）**：锁屏后 ~600ms 内的真实 dismiss 轻点会被吞（需再按一下）——刚锁 <0.6s 就抢跑人脸认证本身即是"锁了又秒解"bug 的温床；壁纸阶段单独轻点 Win/Ctrl/Shift 等纯修饰键不再触发（凭据视图出现后的修饰键按压 MAKE 可见、仍触发）。

### 实验 10 四续：删除时间波形，改输入边沿状态机（2026-08-31，自动化通过、装机验证待做）

三续仍把本机观测到的 33–76ms 自动重复间隔和 600ms 沉降时间写成正确性条件；Windows 键盘重复延迟/频率可配置，这类时间阈值不能证明 Win+L 尾巴安全，且会直接吞掉沉降窗内的真实第一次按键。最终实现删除 `GetLastInputInfo`、`QUIESCE_MS`、沉降窗和 30s 窗口重播种，抽出无 COM 的 `input_trigger_policy.h`：

1. Raw Input MAKE/BREAK 直接进入逐 VK 边沿状态；普通 MAKE 立即触发，壁纸吞 MAKE 时普通孤立 BREAK 仍代表一次完整按压。
2. 初始锁屏轮排水第一条 L 事件链直到 BREAK，孤立 LWIN/RWIN BREAK 永不触发；三种 Win+L 长按释放顺序均与持续时间、自动重复频率无关。无法区分的保守代价缩小为“其它方式锁屏后立即第一次按 L 需要再按一次”。
3. 鼠标移动没有策略入口；壁纸吞掉第一次点击，凭据视图中的第二次完整物理点击在按钮 UP 后形成候选。100ms 可取消窗口让密码/PIN 磁贴切换的 `SetDeselected()` 先停止 watcher，避免摄像头闪开。
4. 失败重试轮启动时种下当前仍按住的键/按钮，重复和释放尾巴不触发，只有新的键盘 MAKE 或完整鼠标点击才能重试。

`CredentialProviderInteractionPolicyTest` 覆盖普通壁纸 BREAK、第二次完整点击、移动无触发、三种 Win+L 释放顺序、保守首 L 以及跨失败轮次的按住/释放尾巴。鼠标候选取消与密码磁贴切换仍需在真实安全桌面装机验证。

### 实验 15：公共命名管道事件驱动迁移（2026-09-01，代码与自动化已完成，装机 A/B 待做）

**动机**：CP 原实现每 50ms `PeekNamedPipe` 一次，终态交付有 0–50ms 调度量化；服务端接受/读取也靠 25/50ms 轮询，并存在连接后立即写入被 `ERROR_NO_DATA` 误断的竞态。服务端 `FlushFileBuffers` 还可能被不读响应的客户端无限阻塞。

**实现**：服务端接受/读/写和 CP 读/写全部迁移到 overlapped I/O，完成事件与停止事件共同等待，取消后回收 I/O；认证终态用 `AUTH_ACK`、控制响应用 `CONTROL_ACK`，ACK 截止 2 秒，删除服务端管道 `FlushFileBuffers` 与伪输出 drain。线格式、DACL、单实例和消息顺序不变，新增 ACK 是同版本组件间的交付协议。

**自动化结果**：CP pending-read 取消 0ms、终态回调内自销毁 0ms、服务停止取消 accept/read 约 110ms（测试含主动 100ms 等待）、静默客户端在约 1.01s 测试截止释放实例；STATUS→终态顺序、连接后立即写入、远程拒绝和 1,000 轮 ACL/内存稳定性通过。该结果证明移除了轮询量化和无界等待，不等于宣称装机感知固定减少 20–40ms；真实收益仍需相同机器的锁屏 A/B 日志确认。

- 三段 A/B：v1 无干预（慢 4/4）→ v2 加解限流（**13/13 全快**）→ v3 移除（**9/10 又慢**，含 2 轮插电）。频率探针（注意：Win11 26xxx 上 `CallNtPowerInformation` 只从 powrprof.dll 导出，ntdl/kernel32 均无；`GetProcessInformation(ProcessPowerThrottling)` 需先填 Version 字段）给出机制：慢轮 P 核全程 1466–1833/2200MHz 且循环尾下坠，快轮钉满 2200，MhzLimit 恒 2200——非硬性限频，是 EcoQoS 启发式压 Session 0 后台子进程，**插电也会发生**，P 核亲和挡不住；预载期推理预热与模式无相关（状态恰在认证窗口内成立）。
